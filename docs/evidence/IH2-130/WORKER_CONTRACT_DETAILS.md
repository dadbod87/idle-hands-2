# Worker preparation: concrete implementation handoff

Planning only; IH2-130 stays queued until127closes. Reuse frozen src/design/audio-sketch.ts, not a speculative src/audio/original-scores.ts path. This is separate from game/runtime integration.

The exact129manifest supplies22050Hzmono frames for each theme and door accent. See audio-worker-bounds.json: compare exact expected frame and ArrayBuffer byte length by whitelist ID rather than accepting arbitrary client durations. Do not send arbitrary score arrays, player state or URLs to the worker. Suggested protocol is a versioned prepare request with monotonically increasing integer request ID, one town/woodland/home ID and optional door flag; one ready response with matching version/ID, exact rate, frame counts and transferable Float32Array buffers. A failure response is a small bounded error code, never an exception dump with paths/state.

A preparer owns at most one live worker and pending promise; replace/cancel/close/timeout rejects that pending request once and terminates its worker. Successful transfer also clears event handlers and terminates the completed worker. Late message/error events cannot resolve another generation or repopulate a future controller cache. A constructor/import must create no worker. Validate requested IDs before construction. Own-worker setup/postMessage exceptions must settle and clean up too. An invalid/malformed ready response must fail closed, without allocating from an untrusted claimed length.

All exact original sample counts are bounded below700000mono frames. Use exact per-ID lengths/rate/buffers, separate caps for door, and reject wrong types, detached/extra channels, mismatched version/ID and over-budget buffers. Renderer validates finite samples in the worker. Whether main repeats that scan is an explicit responsiveness tradeoff to measure; do not conceal synchronous hashing/scanning cost as off-thread preparation. Cross-environment sample identity belongs to acceptance tests, not every playback.
