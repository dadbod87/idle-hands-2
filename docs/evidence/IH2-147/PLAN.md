# Keep shared orchard work private and durable

Match the verified browser practice rules in shared practice. A resident can harvest their own branch and prepare a snack without taking it from another player. Time comes from the shared service. The active resident's current verified feet must be near the matching branch or packing table. Other residents see no private pantry data or resource change.

Prefer adding a nullable JSON column alongside the existing private workshop object on the already locked player row. This keeps older workshop save versions intact, avoids a join or extra snapshot query, and lets the original command receipt commit with the orchard change. No player is proactively populated. Existing permissions stay in force. A corrupt or unknown orchard record stays preserved and disables only orchard writes.

Require an exact command envelope, confirmed resident and server time, a contiguous positional approach, the existing command revision/receipt transaction, matching payload replay, and no separate broadcast. Exercise two residents at the same tree, stale or moved-away requests, invalid recorded data, save/reload/retry, preserved workshop progress and quiet snapshot behavior. Validate only with isolated fictional fixtures. Saved previews, original Idle Hands and hosted services are outside this work.

The source uses the existing single-query private snapshot and the same player row lock as workshop changes. A successful orchard action increments the existing private revision and stores the pantry, workshop revision and exact command receipt in one transaction. The request also carries the expected resident ID, which is checked against the server's authenticated resident. Orchard deadlines are displayed from the last confirmed server clock; there is no extra deadline-triggered fetch. A stored unknown pantry version has a read-only status while ordinary workshop commands still work.
