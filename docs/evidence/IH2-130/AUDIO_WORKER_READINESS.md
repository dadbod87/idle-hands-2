# Optional audio preparation decision — planning evidence, not game integration

Prefer a lazily created dedicated worker to prepare the original score, rather than synchronous main-thread synthesis or downloading the entire3,772,520byte theme WAV pack. Keep the existing129study untouched. No music/sound/context/worker before deliberate enable; a worker is presentation-only and receives theme/accent identifiers, never player data or commands. A future actual Vite-module worker needs its own source/resource/cancellation/browser gates; this isolated Blob-worker probe is not that integration.

Pinned Node24fresh-process reference:18captures (three repetitions per theme/mode). Direct synthesis took31.90–84.16ms, total57.84–139.06ms including import; observed10msmain timer gaps61.43–142.87ms. Worker total73.85–96.70ms (startup/import/termination included), main timer gaps11.14–11.83ms. Do not call this a general speedup: the purpose is moving preparation off the interaction thread.

Direct render27.2–38.8ms and timer gaps27.3–39.1ms; worker render27.4–38.3ms and timer gaps10.7–11.6ms. Observed RAF callback max gaps16.7–33.4msdirect versus16.7–16.8msworker. These are callback observations, not presented FPS, game frames, audio latency, physical-phone/Safari or isolated hardware capacity. Other local work/containers were active. Direct source was parsed before timing; worker total includes startup/parse/message delivery.

All raw Float32PCM hashes match between direct/worker/Node for each original theme. No HTTP/API request, game/database/preview start or AudioContext/audio output occurred. Worker and Blob URL were released after each run. Raw rows, exact source hash, browser version and methods are retained in audio-render-readiness.json and audio-browser-readiness.json; failed values would not be replaced for timing green.

First implementation contract: one pending worker at most; cancel/terminate on mute, hide, close, stale theme or failure; guard late messages with an epoch. Transfer PCM rather than serializing sample arrays; validate rate/length/finiteness before copying to AudioBuffer. Cache at most two decoded themes and one tiny door cue, bound retained bytes/voices and clear transient transferred arrays. One music voice plus one effect; separate gains. Restrain repetition with quiet pauses and follow acknowledged room/context changes, not clicks or provisional movement. No server query, timer/economy rule or progress mutation. Human listening and actual game/physical-device validation remain pending.

[MDN workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers) documents background execution and transfer/message behavior; [terminate](https://developer.mozilla.org/en-US/docs/Web/API/Worker/terminate) stops a worker without waiting for its operation to finish. Browser policies/resource cleanup must be checked in the actual integration rather than inferred from the probe.
